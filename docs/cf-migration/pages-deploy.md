# memo.d.foundation on Cloudflare Pages (CF-N.1)

Config-only prep for moving memo.d.foundation from Railway (Docker + nginx) to
Cloudflare Pages. The live Pages deploy, DNS cutover, and retiring Railway are
**not done here** (deploy-gated: needs the CF Pages project + DNS access owned
by whoever runs the cutover; Railway stays warm until then, per the
megagoal). This doc covers what IS built and validated: the redirect config,
the RSS `?limit=` handling, and the Pages project config.

Read `docs/cf-migration/build-inventory.md` first for the full build pipeline
(vault -> Elixir export -> TS generate-* scripts -> `next build` -> `out/`).
This doc only adds the Pages-specific pieces at the end of that pipeline.

## What changes for Pages vs. the current Railway/nginx deploy

| Concern | Railway (today) | Cloudflare Pages (this doc) |
| --- | --- | --- |
| Static output | `out/` served by nginx inside the Docker image | `out/` uploaded as the Pages build output (`pages_build_output_dir = "out"` in `wrangler.toml`) |
| Redirects | `nginx_redirect_map.conf`, generated by `pnpm run generate-nginx-conf`, included into `nginx/nginx.custom.conf` | `out/_redirects` (fast path, capped) + `functions/_middleware.ts` (full map, no cap) |
| RSS `?limit=` | `nginx.custom.conf`'s `map $arg_limit ...` blocks + `try_files` | Same file-selection logic, reproduced in `functions/_middleware.ts` |
| Build command | `make build-static` (Dockerfile, runs Elixir + `pnpm run build` + `generate-nginx-conf`) | `pnpm run build && pnpm run generate-cf-redirects` (new script, additive; Makefile/Dockerfile untouched) |

Railway's `Makefile`/`Dockerfile`/`nginx/` are untouched by this sub-goal. They
keep working as-is until M5 retires Railway.

## Redirects: `_redirects` vs. the Pages Function, and why both exist

`scripts/generate-cf-redirects.ts` reads the same source data
`scripts/generate-nginx-redirect-map.ts` does
(`public/content/{redirects,aliases,shorten-redirects}.json`, cross-checked
against the actual markdown files under `public/content`) and produces:

1. **`out/_redirects`**, the Cloudflare Pages redirects file. Written
   straight into `out/` (not `public/content/`): Next's static export copies
   everything under `public/` to the *root* of `out/`, so a file at
   `public/content/_redirects` would land at `out/content/_redirects`, not
   where Cloudflare looks for it (`out/_redirects`). `scripts/generate-rss.ts`
   already writes its feed files straight into `out/` for the same reason;
   this follows that convention.
2. **`functions/_generated-redirect-map.ts`**, the FULL redirect map (every
   rule, no cap), auto-generated, gitignored, consumed by
   `functions/_middleware.ts`.

**Why both:** Cloudflare Pages caps `_redirects` at 2,000 static rules + 100
dynamic (splat/placeholder) rules, 2,100 total
(<https://developers.cloudflare.com/pages/configuration/redirects/>). The
current nginx map has ~1,526 rules (see Confirmation run below) which fits
today, but the map grows with the vault (the #302 inventory measured 4,282
raw redirects before the markdown-existence filter; the filtered/served count
will keep climbing as more short-links and renamed pages accumulate). Relying
on `_redirects` alone is a ticking time bomb: the day it crosses 2,000, rules
silently start getting dropped and a reader hits a dead link. So:

- `out/_redirects` carries the first 2,000 rules (sorted, deterministic) as a
  **fast edge-level path**, no Function invocation, lowest latency.
- `functions/_middleware.ts` re-checks against the **full, uncapped map** on
  every request that isn't already resolved by `_redirects`, so nothing is
  ever silently dropped regardless of how large the map grows.

This is belt-and-suspenders by design, not an oversight: `_redirects` is an
optimization, the Function is the correctness guarantee.

## RSS `?limit=` handling

`scripts/generate-rss.ts` already pre-generates every limit variant as a
static file (`rss_10.xml` … `rss_100.xml` in steps of 5, `atom_*.xml`,
`feed_*.xml`, `index_*.xml`, plus the unlimited `rss.xml` etc.). Nginx never
renders anything dynamically for `?limit=`; it just picks which
pre-generated file to serve, via `map $arg_limit ...` + `try_files`, in
`nginx/nginx.custom.conf`. Cloudflare Pages' `_redirects` can't match on
query strings at all (only path/splat), so this needed a small Pages
Function, not a static rule:

`functions/_middleware.ts` (logic factored out to `functions/lib/feed-limit.ts`
for unit testing, see `test/feed-limit.test.ts`):

- For `/rss.xml`, `/atom.xml`, `/feed.xml`, `/index.xml`: a `?limit=N` with N
  a positive integer serves `/{type}_N.xml` via `env.ASSETS.fetch` (the Pages
  Functions static-asset binding); if that exact file doesn't exist (N isn't
  one of the pre-generated multiples of 5, or falls outside 10-100), it falls
  back to the unlimited `/{type}.xml`, mirroring nginx's `try_files
  $limited $uri /404.html` chain. No `?limit=` (or an invalid one) defaults to
  **20**, matching the current site's default (nginx's `map` default is also
  20, not the unlimited feed).
- `/feed/index.xml` gets the same treatment against `/feed_N.xml`, falling
  back to `/feed.xml`.

Everything else falls through to `context.next()` (static asset serving), so
the Function only intercepts the four feed paths + `/feed/index.xml` +
whatever's in the redirect map.

## Known gaps vs. nginx (follow-up, not blocking this sub-goal)

`nginx.custom.conf` has a few more behaviors this sub-goal's scope
(`_redirects` + RSS `?limit=` + Pages config) didn't cover; flagging so they
aren't silently lost on cutover:

- **Trailing-slash normalization** (`/path/ -> /path`, 301). Next's static
  export already controls this via its own `trailingSlash` behavior; verify
  the exported `out/` doesn't need the nginx-side 301 once a real `out/`
  exists to inspect.
- **`_next/data/*.json` cache headers** (`Cache-Control: public,
  max-age=0, must-revalidate`). Cloudflare Pages' default asset caching may
  already behave reasonably here since Next's static export doesn't produce
  per-request-varying `_next/data` files, but hasn't been checked against a
  real `out/` tree.
- **`/tools/` MIME type** (`build-ci-lint` output, forced
  `application/javascript`). Cloudflare Pages generally infers correct MIME
  types from file extensions; low risk, not verified against a real build.

## Reproduce

```
cd memo.d.foundation   # a worktree with node_modules and a fully-built public/content
pnpm run generate-cf-redirects
pnpm run verify-cf-redirects            # diff vs public/content/nginx_redirect_map.conf
npx wrangler pages functions build functions --outdir /tmp/out --compatibility-date 2026-07-23
pnpm exec vitest run test/feed-limit.test.ts
```

To verify against a different, already-built `public/content` (e.g. a sibling
validation worktree) without touching it:

```
tsx scripts/generate-cf-redirects.ts   # cwd's public/content is read; point
                                         # CF_REDIRECTS_OUT_DIR / CF_REDIRECTS_FUNCTIONS_DIR
                                         # at scratch paths to avoid writing into a borrowed dir
tsx scripts/verify-cf-redirects.ts <content-dir> <functions-dir>
```
